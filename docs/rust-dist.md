# Rust CLI distribution

[日本語](rust-dist.ja.md)

Use `.github/workflows/rust-dist.yaml` for a Rust CLI that should publish a crate and distribute prebuilt binaries from the same CalVer release-only commit.

The workflow composes the existing release primitives instead of giving them overlapping ownership:

1. `rust-crate.yaml` allocates a Cargo-compatible CalVer, creates the release-only commit, optionally publishes crates.io, and pushes the immutable release tag.
2. `cargo-dist.yaml` explicitly dispatches the project's dist-generated workflow from that immutable tag.
3. `rust-dist.yaml` waits for the resulting GitHub Release to be published with assets.
4. When crates.io publication is enabled, it runs a real `cargo binstall` acceptance for the exact crate version.

## Project setup

Use a Cargo SemVer-compatible CalVer such as `YYYY.MM.PATCH`. A calendar string such as `YYYY-0M-0D` is not suitable for this Rust distribution path.

Configure dist to accept explicit release dispatches. With the current stable dist release:

```toml
[workspace.metadata.dist]
cargo-dist-version = "0.32.0"
dispatch-releases = true
```

Regenerate and commit the dist workflow:

```bash
dist generate
dist generate --check
dist manifest --artifacts=all --output-format=json --no-local-paths
```

The generated workflow is normally `.github/workflows/release.yml` and must expose the `workflow_dispatch` tag input generated by dist.

## Recommended caller

```yaml
name: Release

on:
  push:
    tags:
      - latest

jobs:
  release:
    permissions:
      actions: write
      contents: write
      id-token: write
    uses: f4ah6o/calver-action/.github/workflows/rust-dist.yaml@<commit-sha>
    with:
      format: YYYY.MM.PATCH
      timezone: Asia/Tokyo
      legacy_prefixes: v
      provenance_file: src/release-commit.txt
      registry_publish: true
```

Pin production callers to an immutable `calver-action` commit SHA.

If the generated dist workflow has a different filename or input name:

```yaml
with:
  dist_workflow_file: release.yml
  dist_tag_input: tag
```

## cargo binstall acceptance

`binstall_acceptance` defaults to `true` when `registry_publish` is `true`.

The acceptance waits until the dist GitHub Release is non-draft and contains assets, then installs the exact released crate version with cargo-binstall. It deliberately selects only the `crate-meta-data` strategy:

```text
cargo binstall --strategies crate-meta-data <crate>@=<version>
```

That disables cargo-binstall's `quick-install` and source `compile` fallbacks for this check. A green acceptance therefore cannot be produced merely because the crate compiles from source or because an unrelated third-party quick-install artifact exists.

The workflow uses cargo-binstall `1.21.1`, currently the latest stable release, and disables telemetry for the acceptance run.

The GitHub Release wait defaults to 180 attempts at 10-second intervals (30 minutes). After the release is ready, cargo-binstall is retried briefly to tolerate crates.io metadata propagation.

For a version-only/internal release:

```yaml
with:
  registry_publish: false
```

The crate release and dist handoff still run, but public `cargo binstall <crate>` acceptance is skipped because crates.io metadata is intentionally absent. Set `binstall_acceptance: false` explicitly as documentation when that is the intended policy.

## Failure boundary

The immutable CalVer tag remains the recovery boundary. If crates.io and the immutable tag succeeded but dist or binstall acceptance failed, fix the artifact/metadata problem and rerun the downstream distribution path for that existing tag. Do not allocate a new CalVer merely to retry binary distribution.

`cargo-dist.yaml` remains available as the lower-level dispatch helper for repositories that need custom orchestration. `rust-dist.yaml` is the default high-level workflow for ordinary Rust CLI releases.
